## What was built

| File | Change |
|---|---|
| `src/dsh/bundle.js` (new) | `state(deps)`, `install(deps)`, plus `describe(state)` (the plain-text status), `locateHarness({env, registry})` and `runCommand(...)` (the default way of running the command), exported so tests can reach them. |
| `src/cli.js` | `dsh bundle status [--json]` and `dsh bundle install [--json]`, handled before `app.snapshot()` (they read no DSHProxy settings, accounts or keys); two help lines; the `dsh` usage line names them. |
| `test/dsh-bundle.test.js` (new) | 34 tests. |
| `test/manual/dsh-bundle-real-run.ps1` (new) | The one real run. A `.ps1` because `node --test` runs every `.js` under `test\`. |

Both functions are `async` (the process list and the command are child processes). Dependencies, each with a real default:

| `deps` | Default |
|---|---|
| `home` | `dshHome()` from `src/dsh/profile.js` (`DSH_HOME`, else `~\.dsh`) |
| `harnessDir` | `locateHarness()`: `%DSHPROXY_HARNESS_DIR%` when set (then nothing else is tried), else `%LOCALAPPDATA%\Programs\DeepSeek Harness`, else the folder of the program in `HKCU\Software\Classes\dsh\shell\open\command` (`reg.exe query`, 5 s). "Found" means `resources\runtime\cli\bin\dsh.cmd` is a file in it. |
| `root` | the DSHProxy checkout (`src\dsh\..\..`); `folder` is `<root>\integrations\dsh-video` |
| `processes` | one `powershell.exe` call, `Get-CimInstance Win32_Process -Filter "Name='DeepSeek Harness.exe'"`, 20 s; an end marker proves the list is whole |
| `run` | `runCommand`: `cmd.exe /d /v:off /s /c ""<dsh.cmd>" plugin --profile desktop add "<folder>" 2>&1"`, verbatim arguments, `cmd.exe` and `taskkill.exe` taken from `%SystemRoot%\System32`, not from `ComSpec` or `PATH` |
| `env` | `process.env` (where Harness is looked for; the base of the child's environment) |
| `timeoutMs` | 120000 |
| `logFile` | `<DSHProxy data folder>\dsh-bundle-install.log` (`DSHPROXY_HOME`, else `~\.dshproxy`); overwritten by each run |
| `registry` | the `reg.exe` reader above |

How the rules are met:

- Read-only: `state` only reads files and the process list. `install` writes one file of its own, the log, in DSHProxy's data folder, and only when the command was run.
- No write into a profile: there is no `fs.write*` on anything under the Harness home in `bundle.js`.
- Once: `install` calls `run` in one place, with no loop. A rejected `run` is caught and reported, not repeated.
- Timeout: `taskkill /T /F /PID <cmd.exe>`, then the result is a second `look`. If something that outlived the tree still holds the output pipe, the wait ends 5 s after the kill.
- Unsafe characters are refused twice: in `state` (`canInstall: false` with the reason) and again inside `runCommand`, which also refuses a part ending in a backslash (it would swallow the closing quote). The same check covers the path of `dsh.cmd`.
- Child environment: every name matching `^DSH_` in any letter case is dropped, `ELECTRON_RUN_AS_NODE` is dropped, `DSH_HOME` is set to the home in use. `DSHPROXY_*` is kept (it does not start with `DSH_`).

## Where the contract left a choice

1. **`log`**: I made it DSHProxy's own record of the run (command line, exit code, whole output), not Harness's `pnpm.log`. Harness's log does not exist when its command fails before pnpm starts, and Harness's own failure line already names it. `null` when nothing was run or the file could not be written.
2. **`reason` when `bundle` is `installed`**: empty, even when Harness is running or not found: there is nothing to install. The one exception is a patch that cannot be read (point 4).
3. **Which reason, when several apply**: Harness not found, profile missing, `package.json` unreadable, patch unreadable, switched off, DSHProxy's own folder missing, unsafe path, process list unreadable, Harness running. "Quit Harness" comes last so that nobody quits it for an install that would be refused anyway. `harnessRunning` is reported in every case.
4. **`bundle` when a file cannot be parsed**: the contract has no "unknown". Unparseable `package.json`: `not-installed`, `linkedTo: null`. Unparseable patch: the value `package.json` alone gives (so possibly `installed`), with the reason saying it is not known whether the plugin is switched on; `install` then answers `ok: true, "already installed ..."` followed by that reason, and runs nothing (test: `a linked and selected plugin with an unreadable patch reads installed, with the doubt said, and nothing is run`).
5. **A dependency that is not a `link:`** (a version, a tarball, `file:`): `other-folder` with `linkedTo: null`, so `canInstall` can be true and the command replaces it.
6. **`version`**: the `version` in the `package.json` of the folder the profile points at; `null` when not installed or the folder is gone.
7. **`harnessRunning` when Harness is not found**: `false`, and the process list is not read (there is no folder to match against). A `DeepSeek Harness.exe` whose program path Windows does not give counts as running.
8. **Failure without `--json`**: the message goes to standard output and the exit code is 1 (as `dsh verify` does), not through the `DSHProxy: ...` error path.
9. **The path of `dsh.cmd`** gets the same unsafe-character check as the folder, since it goes through `cmd.exe` too.
10. **`DSHPROXY_HARNESS_DIR` set but without the command in it**: not found; the other two places are not tried ("when set").

## Concerns

- **Read word for word, the contract misses two things research section 7 lists.** `state` reads `dependencies` only, not `devDependencies` or `optionalDependencies`, and the profile's `cordis.patch.yml` only, not the home-level `<home>\cordis.patch.yml` that applies to every profile. A plugin disabled in the home-level patch reads `installed`. I kept to the contract; each is a few lines if wanted.
- **A relinked plugin can end `switched-off`.** Harness's command does not select a dependency that was already in `package.json`. From `other-folder` or `folder-missing` with the name missing from `dsh.profile.bundles`, `install` therefore ends `ok: false, bundle: "switched-off"` with a message to switch it on in Harness. Shown with the stand-in (`a plugin relinked from another folder that was not selected ...`), not with the real command. Spec criterion 6 ("with the repair") holds only when the name is still selected.
- **Not tried for real**: a failing or hanging real command, and a machine where `powershell.exe` or CIM is unavailable (there every status says Harness is running). The registry fallback was tried once, read only: `locateHarness({ env: {} })` returned `C:\Users\USER\AppData\Local\Programs\DeepSeek Harness` from the real key. The value name `reg.exe` prints is localised; the parser keys on `REG_SZ`, which is not, but only an English Windows was checked.
- **`src/dsh/profile.js`**: nothing copied; `dshHome` is exported and used as is.
