## What to build

1. `login`: register the client for `authorization_code` and `refresh_token` (only when the server's metadata lists `refresh_token` among its grant types; otherwise as today). Store the client id, and the refresh token when the token answer carries one, with the same protection as the access token (the store encrypts the whole session; look at how). A sign-in started with `--client-id` keeps working.
2. `access`: when the stored access token is expired or within the existing 30-second margin (choose and state a renewal margin; a call must not start with a token that dies mid-call, and a job poll can run for minutes), make one refresh request: `grant_type=refresh_token`, the refresh token, the client id, and the `resource` the helper already sends. Validate the answer as strictly as the first token answer is validated today. If it carries a new refresh token, that replaces the old one. Store the renewed session before returning the token.
3. Two helper processes can need a renewal at the same moment (the app polls status while a command runs). With rotating refresh tokens the second request would be refused and could wipe a good session. Exactly one of them refreshes; the other waits and reads the result (criterion B3). Say in the report how you guarantee it and what happens if the process holding the lock dies.
4. Failure rules (criterion B4): a refused refresh (`invalid_grant`, or any 4xx) removes the session and the call ends as sign-in required. A network error, a timeout or a 5xx leaves the stored session untouched and ends as sign-in required for this call only. Never fall back to an expired access token.
5. `status`: still one JSON line with `signedIn` and `expiresAt`; add a boolean that says whether the session can renew. `signedIn` is true for a session whose access token has expired but which can renew. The desktop app parses this line today and must not break on the new field: check how `bin\dshproxy-krea.js` prints it and say in the report what the app reads (it is C#, in `app\DSHProxyApp.cs`; read only).
6. A session file written by the shipped helper (no client id, no refresh token) keeps working until it expires, then needs a new sign-in.
