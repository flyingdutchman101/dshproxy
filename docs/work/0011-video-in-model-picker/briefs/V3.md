# Brief: V3 — video models by resolution, Flux 3, and entries that can be switched on

## Objective

DSHProxy's video catalog knows, for each model, each resolution and each billing route, whether that combination exists and what the reference clip (5 seconds, 16:9, text only) costs. Flux 3 is a fifth model. Every video command takes a resolution. A combination that exists is an **entry**; the user can switch entries on and off with a command, and code that comes later (the chat model picker) can list the entries that are on, each with a name like "Seedance 2.5 - 720p - Krea".

## What to build

1. **Catalog** (`src\video\catalog.js`). Keep `models`, `quote`, `routesFor` working for today's callers. Add:
   - Per model, per route, per resolution: does it exist, the provider's model id (and for VideoRouter the host the price belongs to), the reference clip's price (US dollar micros, or plan credits for Callirra), the date and the source URLs. For the `krea` route there is no fixed price: the entry says "quoted live in workspace units" and may carry the units recorded on 2026-11-22 as a dated reference, marked as such.
   - `entries()`: every combination that exists, each `{ model, resolution, route, label, ... }`. `label` is "Model - resolution - Provider", with the names a person knows: "Seedance 2.5", "Seedance 2.0", "MiniMax H3", "Wan 3.0", "Flux 3"; "VideoRouter", "VideoRouter (Replicate)", "KovAPI", "Callirra", "Krea". A fixed tier (MiniMax H3 on Krea) shows the tier's name where the resolution would be, as the provider states it; do not invent a resolution for it.
   - `quote(model, route, resolution)`; with no resolution it answers as today (the 720p figures, 768p for MiniMax H3, must equal today's numbers exactly).
   - `flux-3`: on VideoRouter (720p, 1080p) and on Krea (`black-forest-labs/flux-3-video`, 720p and 1080p, no 480p).
   - **Nothing is interpolated or guessed.** A combination without a published price from the documents above is not an entry. Seedance 2.5 has no 768p. If the documents disagree or a figure is missing, leave the combination out and list it in your report.
2. **Resolution on every route** (`command.js`, `transport.js`, `workspace.js`). `video quote`, `video submit` and `video status` take `--resolution R`; without it they behave as today. A combination that is not an entry is refused before any request is made. For the API routes (VideoRouter, KovAPI, Callirra), the request carries the resolution in the way that provider's documentation states. You may read the providers' public documentation on the web to confirm the parameter name and value format; cite the URL in a comment next to it. **If you cannot confirm from the provider's own documentation how a resolution is sent, do not send one: that resolution is then not an entry on that route** (a wrong or ignored parameter would buy a different clip than the one quoted). VideoRouter requests name the host the price belongs to and switch fallbacks off, as today's code does for 720p.
3. **Entries that can be switched on** (`settings.js`, `command.js`). `dshproxy video entries` lists every entry with on or off; `dshproxy video entries set MODEL RESOLUTION ROUTE on|off` switches one. All are off until switched on. They are stored in the existing video settings file beside today's settings, which keep their meaning; an older file without entries reads as all off; a file with an entry that no longer exists is read without failing and that entry is dropped on the next write. Export a function that returns the entries that are on, for later code. The existing rules of that file apply (it holds names and booleans only, never a credential; concurrent writers do not lose each other's change: see how `settings.js` and `test\video-concurrency.test.js` do it today).
4. **The Harness bundle keeps its answers** (`integrations\dsh-video`). Its four tools give the same answers as before for existing settings (criterion C5). Two loose ends from an earlier review belong here: `runner.cjs` recognises a resolution with a pattern like `\d{3,4}p`, which does not fit a fixed tier; and the bundle's closed set of job statuses must agree with what the command line can return. Fix both with tests, without changing what a user sees for today's settings.
