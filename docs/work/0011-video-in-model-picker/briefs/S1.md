## Objective

Build the core of a module that answers "video entries" picked in a chat application's model picker: a typed prompt gets a price quote; a confirming reply buys one paid video clip. ## What to build

New files only:

- `src\video\picker\index.js`: `create(options)` returning at least `{ answer(body, write) }` with the options of design 9.3 (`home`, `ops: { quote, submit, status }`, `clock: { now, sleep }`, `random`, `entries`, `exposed`, `log`).
- `src\video\picker\store.js`: the journal of amendment A1 (create, claim by append-flush-read-back, first record wins, damaged lines), write-once files for quotes, outcomes and results, reading them as design 5.1 says.
- `src\video\picker\flow.js`: the answer for a prompt (quote), for a confirmation (the steps of 5.2 with A1), and for a request about a quote that is already claimed (5.4).
- `src\video\picker\classify.js`: only what S1 needs: finding the quote in the assistant turn before the reply, the units after it, and the confirmation rule of 4.2 with the user's words (amendments, answer 2). It must already be total: it never throws, whatever the body (A3).
- `test\video-picker-once.test.js`: the five tests of design section 13, in that order, plus what the journal needs (below).

`answer(body, write)` takes a parsed request body (Anthropic messages shape: `model`, `system`, `messages`) and writes text pieces through `write`; its promise resolves when the answer is complete. Entries come from the injected `entries()` (a `Map` from id such as `seedance-2.5/720p/krea` to `{ model, resolution, route, label, unit }`); do not read any catalog or settings.

Rules that are not negotiable:

- The claim is made, flushed and read back **before** `ops.submit` is called. `ops.submit` is called at most once per quote id, ever, by any number of pickers on the same folder.
- Nothing is sent again because time passed, because a file is missing, or because an earlier attempt's outcome is unknown.
- No lock that can be taken from a live holder; do not use `src\filelock.js` for the claim.
- A purchase is refused while the journal is younger than 60 seconds (A1). Tests set the journal's age through the injected clock or by creating it earlier; do not weaken the rule to make a test easier.
- The texts are the design's (6.1 to 6.4, A6): plain sentences, the quote id on its own last line as designed. No stack trace, no file path, nothing from the environment in any answer.
- For this slice, purchases are always "on" and there is no ceiling: those belong to the next slice. Leave one obvious place in `flow.js` where the next slice adds them (between the claim and the submit, as design 5.2 step 3 says), without building them.

## Acceptance criteria

1. Tests 1 to 5 of design section 13 pass. Test 5 is an invariant over seeded random sequences of quote, confirm, repeat, "restart" (a new `create` on the same folder), clock jump, fork (two bodies sharing a prefix) and expiry: `submit` is called at most once per quote id, and never for a quote that fails the checks C1 to C5 of design 3.4. Print the seed on failure; run at least 500 sequences.
2. Journal tests: two pickers on one folder claim the same quote at the same moment and exactly one holds it; a journal whose last line is torn (no final newline, cut in the middle of a record) still gives the right answer for that quote (claimed, unknown) and for the next quote (it can be claimed, and its record is not glued to the torn line); a line that is not a record but contains a quote id counts as a claim; a failed flush or read-back sends nothing; the journal is never truncated or rewritten (compare its bytes before a claim with its prefix after).
3. One test with real processes: start N (at least 8) Node child processes that each try to claim the same quote id on the same folder through `store` at the same moment (use a file or a time as the starting signal); exactly one reports that it holds the claim. Repeat 20 times. This is the only test that may start processes; none of them calls `submit`.
4. **Mutation evidence.** Run tests 1 to 5 once against a copy of `flow.js` in which the claim step is skipped (for example through an environment variable read only in the test copy, or a temporary edit you revert), and show in the report that they fail with two `submit` calls. Also show the journal tests failing when "first record wins" is replaced by "last record wins". Leave no mutation switch in the shipped code.
5. `classify` total: a test feeds `answer` bodies with `system` as a list, `content` as a string, a number, `null`, missing `messages`, an empty `messages`, a 2 MB string: no throw, no purchase, no quote request.
6. No existing file is changed. `node --test` and `node scripts/check.js` pass.
